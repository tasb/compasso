# Compasso 3.2.0: upgrade notes

Read this whole file before changing anything. It says what changed, what is new, and what to do in each project. Act on a project's tracker only with the persona that step names, and show the person what a step will change before you change it.

Most of 3.2.0 changes `stage: mvp` only. A project in `production` keeps 3.1.0's merging, findings and pipeline.

## What changed

- **In `mvp` only blocker and major findings are fixed in the story.** A story's open minor findings are filed together as one issue for after the MVP: labelled `compasso::after-mvp`, in no sprint, never assigned during the MVP. `/compasso:plan` offers them once the stage is `production`, and `/compasso:harden` lists a feature's.
- **Every follow-up can be checked by a test.** A finding to be filed carries an acceptance line (Given/When/Then) written by its reviewer, and a follow-up's Verify lists real commands. Before, a follow-up's acceptance was "When it is reviewed again, Then the finding no longer applies", and its Verify "the repo tests".
- **A severity floor.** Anything that can leak or destroy data, widen access, fail open or break production is at least major, in every stage.
- **In `mvp` a change merges on green.** When nothing needs a person, the developer sets its own merge request to merge as soon as it opens it; the tracker merges it once its pipeline passes. There is no approver and no "behind its target" rule. The tech lead handles a change a person must approve, a rejection and a red main.
- **A red main stops merges** in `mvp`. When the default branch's last finished pipeline failed, the tech lead turns off auto-merge on every open merge request, files the fix as a blocker bug (`compasso::fix-main`), and assigns it at once to the developer whose merge broke main. Only that fix merges until main passes again; then the merge poll sets the others to merge again.
- **In `mvp` the tech lead answers questions on its own,** unless the answer changes scope, security or cost. Its hand back lists every answer it sent, so a person can overturn one.
- **A developer keeps building:** after a batch it takes the next one in the same tick.
- **Unbuildable stories never reach a developer** (team projects). A story or bug with no acceptance (a bug: no Expected), no Verify, or a `dev::` label naming no one in the team is "not ready": nobody builds it or is assigned it, and the tech lead's inbox lists it to fix.
- **A story whose paths overlap a merge request still open waits** until that merge request merges.
- **Verify runs each command once.** A story's Verify command that is the same as one of the repo's commands is skipped, and the output says so.
- **The `mvp` pipeline is lighter.** In `mvp` the merge request pipeline runs verify and the security scans only: no e2e job, no coverage jobs. They come back when the stage is `production` and the pipeline is generated again.
- **Sensitive paths in `mvp`** still need no person, but the merge request's Merge line and the tech lead's review name them as a warning.

## What is new

- `team.sh main` (tech lead): whether main is red, and what broke it. When main is red it turns off auto-merge on every merge request that had it.
- `team.sh fix-main --title T --body-file F [--parent N]` (tech lead): files the fix for a red main, once.
- `team.sh merge` is allowed to the story's developer in `mvp`, for a change no person must approve.
- `tracker.sh main-pipeline`, `disarm` and `close`, the primitives behind them, in both adapters.
- `bin/followups.sh legacy [--close]`: lists the open follow-ups whose acceptance no test can check, in any sprint. With `--close` it comments on each with the story it came from and closes it.
- `bin/version.sh`, run by `/compasso:start` and `/compasso:status`: warns when the running Compasso is older than the newest one installed.
- Labels `compasso::after-mvp` and `compasso::fix-main`.
- An agent continued with SendMessage after a dispatch that was never bound to its run no longer fails with "unknown role 'null'". Name the run folder in the message; the hook says so when it is missing.

## What to do in each project

1. **Update the plugin and restart.** Run `claude plugin marketplace update compasso` and `claude plugin update compasso@compasso`, then restart the session. Run `/compasso:status`: if it warns that a newer Compasso is installed than the one running, restart again, until it no longer warns. Every skill must run 3.2.0.
2. **Labels (the tech lead, or the default persona).** Run `bash ${CLAUDE_PLUGIN_ROOT}/bin/tracker.sh ensure-labels --repo .`. It creates the two new labels and changes no other.
3. **The pipeline (projects in `stage: mvp`; the tech lead, or the default persona).** Run `bash ${CLAUDE_PLUGIN_ROOT}/bin/ci.sh --repo .`, show the person the diff of `.gitlab/compasso.gitlab-ci.yml` (GitLab) or `.github/workflows/compasso.yml` (GitHub), and after their yes commit it through a merge request. Without this step every merge request still runs e2e and coverage. A project in `production` has nothing to do here. When the project later switches to `production`, run `ci.sh` again (setup does it).
4. **Old follow-ups (the tech lead, or the default persona).**
   1. Run `bash ${CLAUDE_PLUGIN_ROOT}/bin/followups.sh legacy --repo .`. It lists the open follow-ups whose acceptance no test can check, and changes nothing.
   2. Show the list to the person. Say that each will be closed with a comment naming its story, and that one still worth doing should be filed again by a person, as a story whose acceptance a test can check.
   3. After their yes, run it again with `--close`.
5. **Stories that are not ready (team projects, the tech lead).** Run `bash ${CLAUDE_PLUGIN_ROOT}/bin/team.sh inbox --repo .`. A "Not ready" line lists the stories no developer can build, with what each lacks. Show them to the person and fix each story (`/compasso:plan` or `/compasso:feature`): acceptance a test can check, Verify commands, or the right developer.
6. **Configuration.** Nothing: 3.2.0 adds no configuration key.
7. **Coming from a version before 3.1.0:** first read [3.1.0.md](3.1.0.md) and follow its "What to do in each project" section. Its step 2 (configuration) is optional.

## Check

- `/compasso:status` shows no warning about a newer Compasso.
- In `mvp`, a story merged after the upgrade had its merge request set to merge by its developer, and its open minor findings, if any, are in one `compasso::after-mvp` issue with an acceptance line each.
- `team.sh main --repo .` (tech lead) answers `"red": false` while the default branch is green.
- `followups.sh legacy --repo .` lists nothing.
