# Compasso 3.1.0: upgrade notes

Read this whole file before changing anything. It says what changed, what is new, and what to do in each project. Act on a project's tracker only with the persona that step names, and show the person what a step will change before you change it.

## What changed

- **Findings are fixed in the story, minors too.** Before, a minor finding became a follow-up story in no sprint. Now every finding is fixed before the merge request merges. A follow-up is filed only for a minor finding whose fix needs someone other than the developer: a person, or an admin of an outside system (for example the cloud organisation's). The finding says who in `needs`. The follow-up is labelled `owner::human` and goes into the story's sprint. The findings are also posted as a comment on the story.
- **Follow-ups keep their labels in team projects.** Before, a team project filed every follow-up with no label and no sprint, so nobody saw it. That was a bug.
- **No stacking.** A story no longer builds on another story's unmerged branch: it waits until what it depends on is merged, and its developer takes other work. `tracker.sh open-mr --target` and `tracker.sh open-mr-branch` are gone.
- **Main stays green.** No merge, in any mode, when the merge request's pipeline failed. Before, GitLab merged such a merge request at once when "Pipelines must succeed" was off. In a team project the tech lead merges only a branch that is:
  - up to date with its target;
  - free of conflicts;
  - not still running its pipeline.
- **The queue counts only what can be built.** A developer's backlog counts toward `team.queue` only for stories with nothing open ahead of them. The tech lead assigns first the stories that can start and hold up the most others. Work for a person (`owner::human`) is never given to a developer.

## What is new

- `team.sh update --iid N` (tech lead): brings a merge request's branch up to date with its target. On GitLab this is a rebase; on GitHub, "update branch". Its pipeline runs again, and a later poll merges it.
- `team.sh review` reports `behind`, `pipeline` (`success`, `failed`, `running` or `none`) and `conflicts`.
- `tracker.sh mr-checks` and `mr-update`, the primitives behind them.
- **Two polls for the tech lead,** each in its own session:
  - `/compasso:work --merge` every `team.lead_merge_minutes` (new key, default 15);
  - `/compasso:work --flow` every `team.lead_poll_minutes` (30), for questions, the queue and work with no developer.

  A plain `/compasso:work` still does both.
- `bin/followups.sh --repo . [--milestone S<n>] [--apply]`: lists the open follow-ups in no sprint and, with `--apply`, moves them into the sprint.
- The approver's folder is per version of the change (`.compasso/runs/lead-<mr>-<patch id>`). A rebase that changes nothing keeps its verdict and does not spend another approver run.

## What to do in each project

1. **Update the plugin and restart.** Run `claude plugin marketplace update compasso` and `claude plugin update compasso@compasso`, then restart the session.
2. **Configuration (tech lead, or the default persona).** Run `/compasso:setup`. Its first step runs `config.sh upgrade`, which adds `team.lead_merge_minutes: 15`. No key needs a value from you; a project without the key uses 15. Commit `.compasso/project.yaml`.
3. **Tracker settings (team projects; a Maintainer does this).** Ask a person with the rights to set them:
   - GitLab, Settings > Merge requests: merge method "Merge commit with semi-linear history", and "Pipelines must succeed".
   - GitHub: in the default branch's ruleset, turn on "Require branches to be up to date before merging".
4. **The polls (tech lead).** Stop the old `/loop <n>m /compasso:work`. Start `/loop 15m /compasso:work --merge` in one session. Ask the person to start `/loop 30m /compasso:work --flow` in a second session on the same checkout. Developers keep `/loop 60m /compasso:work`.
5. **Existing follow-ups (tech lead).**
   1. Run `bash bin/followups.sh --repo .` from the plugin's folder (`${CLAUDE_PLUGIN_ROOT}/bin/followups.sh`). It lists the open follow-ups in no sprint and changes nothing.
   2. Show the list to the person.
   3. After their yes, run it again with `--apply`. It moves them into the current sprint, where the queue assigns them like any story.
   4. A follow-up that only a person can do (for example a cloud organisation policy) should be labelled `owner::human` by hand, so no developer gets it.
6. **Stacked merge requests already open.** Do not retarget them by hand: that would pull the parent's unmerged work into the default branch. Merge from the bottom of each chain up. When a merge request merges and its branch is deleted, the tracker retargets the next one to the default branch, and the merge poll brings it up to date. A bottom merge request that conflicts with the default branch goes back to its developer to rebase.
7. **A red default branch.** Until the default branch is green, every merge request's pipeline fails on top of it. Make fixing it the first story: assign the bug to a developer, and merge its fix before anything else.

## Check

- `/compasso:work --merge` shows only the merge requests in review.
- `team.sh inbox --repo . --json` shows, for each developer in `queue`, `ready` next to `backlog`, and a `human` list.
- A story merged after the upgrade has a findings comment on the story itself.
