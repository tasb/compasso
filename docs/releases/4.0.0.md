# Compasso 4.0.0: upgrade notes

Read this whole file before changing anything. 4.0.0 replaces how the team works: the polls, the story and sprint flows and their agents are gone, and a runner started by cron does one job at a time. It says what changed, what is new, and what to do in each project, step by step. Some steps are a person's: they are marked **(person)**.

## Why

On one team's tracker in `mvp`, after a month: 0 of 35 features closed, 77% of the tech lead's polls found nothing to do, 261 questions went to the person, and sessions ran for weeks while the agents went round the same work. Every change carried the whole process (tester, builder, reviewer, security, approver, shipper, budgets, polls). 4.0.0 keeps that weight for `production` only, and makes the MVP fast: fail fast, fix fast.

## What changed

- **The runner replaces the polls.** Cron starts `bin/run.sh` on each agent's machine: the tech lead every `run.lead_minutes` (15), a developer every `run.dev_minutes` (10). Each run reads the tracker once (`tracker.sh snapshot`) and picks one job (`bin/next.jq`). With nothing to do no model starts. Each run first brings its checkout to the default branch as origin has it, so what is merged there (the stage, `run.*`) reaches it; a checkout with uncommitted changes is left alone. A job runs in a fresh headless session, `/compasso:lead <job>` or `/compasso:build <job>`, for at most `run.job_minutes` (60). Answering a question, reverting what broke the default branch and assigning stories run in the shell, without a model.
- **Stages decide the checks** (`stage`):
  - `mvp`: the pipeline's secret and SAST scans, and the tech lead's one review pass that looks only for blockers (an acceptance line not met or not tested, data loss, a leaked secret, a change that breaks the default branch). Everything else goes to one after-MVP list and never becomes work in the MVP.
  - `harden`: as `mvp`, plus one audit of the whole code by the tech lead; the after-MVP list is drained into stories under one hardening feature.
  - `production`: the reviewer and security agents read every merge request beside the tech lead, one pass each; blocker and major findings send it back once, and a second rework goes to a person. The tester writes the tests, and coverage gets one extra pass.
- **No permission prompts.** `mvp` and `harden` jobs run with permissions bypassed (Codex: approvals and sandbox bypassed); `production` jobs run only the repo's commands, git, the tracker CLI, Compasso's scripts and agents, and `run.allow`.
- **Verify commands run without approval in every stage.** `trust.verify_approval: true` brings the approval back. Without it, anyone who can edit a story on the tracker chooses commands the agents run: turn it on for a tracker people outside the team can edit.
- **A person is asked through a `needs::human` issue** (`bin/human.sh`): what is needed, why (the evidence), numbered steps, and what the agents do meanwhile, assigned to `people.ask`. The person answers there and closes it; the runner frees the story at its next run. A job that fails `run.failures` times (2) asks a person the same way and is skipped until that issue is closed.
- **Bugs first.** Bugs, the most severe first, go before any story; then the earliest sprint. The tech lead may start a later sprint's stories before the current sprint ends.
- **The tech lead writes the stories on the tracker** (`lead.sh story`, from the next feature in the earliest sprint). `plan.yaml` and `/compasso:plan` remain for the first plan.
- **A feature is delivered on staging.** A green default branch deploys itself there (`staging.deploy`, a new pipeline job). When a feature's stories are all closed, the tech lead asks `people.ask` to test it, with numbered steps that start at `staging.url`, and closes the feature.
- **A red default branch is reverted.** The runner opens a merge request that reverts the merge that broke it (`compasso::fix-main`) and reopens its stories; a fix that fails goes to a person.
- **Lessons come from rework.** When a blocker is a mistake a rule would have prevented, the tech lead's rework comment ends with a `Lesson:` line, and the developer commits it to `docs/learnings/` with the fix. Developers recall lessons before each story; the tech lead before each review.
- **The report's agent effort comes from the runners.** Each job's line in `events.jsonl` has its stories and the session's tokens and cost (subagents included) when the harness reports them. `/compasso:report` reads this machine's file, or each machine's with `metrics.sh collect --events`.
- **The merge request description** has only what changed, how to test it and, in `production`, the coverage. The review is the tech lead's comment.

## What is removed

- Commands: `/compasso:work`, `/compasso:sprint`, `/compasso:story`, `/compasso:feature`, `/compasso:review` and the manual `/compasso:harden` (mutation testing, fuzzing, ZAP, performance, accessibility checks).
- Agents: approver, shipper, mutator, finops, builder. The planner, tester, reviewer and security remain.
- The agent-run budget (`budget.sh`, `limits.agent_runs`, the hook's budget guard). `run.job_minutes` bounds each job.
- `team.sh` (join blocks, messages, inbox, claims, polls), follow-ups, the daily digest, the risk-based merge (`approvals.merge`, `risk.sh`, `review-gate.sh`), merge request reports, the sprint's test guide and regression flow.
- Configuration keys: `limits.agent_runs`, `approvals.merge`, `harden.*` (its Playwright image is now `prototype.image`), `test_guide`, `sprint.parallel`, `risk.*` except `risk.sensitive_paths`, `team.poll_minutes`, `team.lead_poll_minutes`, `team.lead_merge_minutes`, `team.agents`, the removed agents' models. `trust.mvp_approval` is now `trust.verify_approval`.
- Labels Compasso no longer uses: `needs::approval`, `needs::lead`, `compasso::auto-merged`.
- The hook that showed local runs after compaction.

## What is new

- `bin/run.sh lead|dev`, `bin/next.jq`, `bin/lead.sh` (merge, rework, later, hardening, story, deliver, red-main), `bin/human.sh ask`.
- `bin/cron.sh --repo .`: prints this checkout's crontab line, through `~/.compasso/bin/compasso-run`, a path no plugin update moves (it starts the newest Compasso installed).
- `/compasso:status` (`bin/status.sh`): the stage, the default branch's pipeline, what waits for a person, the merge requests, each developer's work, the job the runner starts next for each role, and this machine's last runs.
- Configuration: `run` (lead_minutes, dev_minutes, job_minutes, failures, allow), `staging` (deploy, url), `people.ask`, `team.developers`, `trust.verify_approval`, `prototype.image`.
- Labels: `needs::human`, `compasso::rework`, `compasso::fix-main`, `compasso::after-mvp` (the one list), and `dev::<name>` for each of `team.developers`.

## What to do in each project

Do these in order, in the tech lead's checkout unless a step says otherwise. Stop and tell the person when a step fails.

1. **(person) Stop the old polls, and clean the agents' checkouts.**
   1. In every agent session that runs `/loop ... /compasso:work` (the tech lead's two, each developer's), stop the loop and close the session. 4.0.0 has no `/compasso:work`: a loop left running only prints an error.
   2. In each agent's checkout, `git status` must show nothing to commit: commit and push, or discard, what is there. The runner moves the checkout to the default branch before every run, and leaves a checkout with uncommitted changes where it is.
2. **Update the plugin and restart.** `claude plugin marketplace update compasso` and `claude plugin update compasso@compasso`, then restart the session. On Codex: `bash <engine>/bin/install-codex.sh` once per machine, then `install-codex.sh --repo .` in each checkout. Run `/compasso:status`: if it warns that a newer Compasso is installed than the one running, restart again.
3. **Configuration.** Run `/compasso:setup` in the tech lead's checkout. It first runs `config.sh upgrade`, which renames `trust.mvp_approval` and `harden.images.a11y`, drops the removed keys, and adds the new ones. Then answer, with the person: `stage`, `staging.deploy` and `staging.url`, `people.ask`, `team.developers` (the developers' names: the same as their `dev::` labels), `run`, and `trust.verify_approval`. Commit `.compasso/project.yaml` and merge it to the default branch.
4. **Pipeline.** `bash ${CLAUDE_PLUGIN_ROOT}/bin/ci.sh --repo .`, then commit what it wrote (`.gitlab/compasso.gitlab-ci.yml`, or `.github/workflows/compasso.yml`). It adds the staging deploy job when `staging.deploy` is set.
5. **Labels.** `bash ${CLAUDE_PLUGIN_ROOT}/bin/tracker.sh ensure-labels --repo .`. Then, **(person)** on the tracker, remove `needs::approval` and `needs::lead` from any open issue or merge request: nothing reads them now.
6. **Feature states.** The runner plans only features in `compasso::new` and delivers only those in `compasso::building`. List the open `type::feature` issues and their `compasso::` label, show the person the list, and with their yes set each with `tracker.sh set-state --repo . --iid <feature> --state <state>`:
   - `compasso::verifying` (3.x), or no state but with stories already planned: `building`. The tech lead delivers it once its stories are closed.
   - no state and no stories yet: `new`. The tech lead splits it into stories when its sprint comes.
   From 4.0.0, `push-backlog` creates features in `new` and `push-plan` moves them to `building`.
7. **The after-MVP issues of 3.2.0.** They were one issue per story; 4.0.0 reads one list (`lead.sh later`), and the old issues are never assigned. Show the person how many there are and ask before moving them. With a yes, for each one: write its description to a file, `bash ${CLAUDE_PLUGIN_ROOT}/bin/lead.sh later --repo . --body-file <file>`, then close it with a comment that names the list (`tracker.sh close --repo . --iid <old> --body-file <comment>`).
8. **Each developer's checkout.** In each one, run `/compasso:setup` as that developer: its name must be in `team.developers`. Then `/compasso:status`.
9. **(person) Start the runner on each machine.** In each checkout (the tech lead's and every developer's), run `bash ${CLAUDE_PLUGIN_ROOT}/bin/cron.sh --repo .` and give the person its line. The person then, on that machine:
   1. `crontab -e`, pastes the line, saves.
   2. `crontab -l` shows it.
   3. After the first period, `tail .compasso/runs/runner/cron.log` shows a run (`nothing to do` is a run). On macOS, `Operation not permitted` means cron needs Full Disk Access (System Settings > Privacy & Security); grant it and wait for the next run.
10. **Old files.** `.compasso/runs/.working` and `.compasso/runs/*/budget.jsonl` are no longer used; delete them if you like. Lessons in `docs/learnings/` that name the `builder` role stay valid.
11. **Coming from a version before 3.3.0:** read [3.3.0.md](3.3.0.md) for its plan changes first; its other steps are replaced by these.

## Check

- `bash ${CLAUDE_PLUGIN_ROOT}/bin/config.sh validate --repo .` passes, and `.compasso/project.yaml` has no `limits.agent_runs`, `approvals.merge` or `trust.mvp_approval`.
- `/compasso:status` shows no warning about a newer Compasso, and a next job (or nothing) for the tech lead and each developer.
- After one period, every machine's `.compasso/runs/runner/events.jsonl` has a line per run, and `cron.log` no errors.
