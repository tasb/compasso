A plugin for Claude Code and Codex · GitLab or GitHub

From rough ideas to merged, reviewed code. One sprint at a time.

Compasso turns what you have into a product brief, a backlog, an architecture and a roadmap. Then it builds each sprint story by story: failing tests first, scripts that stop bad work, review and security review, and a pull request on your tracker. You make the decisions; the agents do the work in between.

Spec-driven planning

Every story is written before it is built: acceptance in Given/When/Then and the commands that verify it. A script checks sizes, dependencies and capacity before anything reaches the tracker.

Test-driven building

A tester agent writes failing tests first. The builder makes them pass with the smallest change and can never edit a test: the files are hashed.

Sprint-paced delivery

Only the next sprint gets stories. Each close measures what was done and re-places what is ahead, MVP first. The tracker always shows the truth.

Present, at any point
1

Start from what you have

/compasso:start

No sprint goal needed. Bring loose notes, a document, issues already on the tracker, or a running prototype. /compasso:start says where the product stands and runs the next step.

The clinic brings an interview with the owner and reception, three issues the owner opened, and a clickable prototype of the booking screens.

Other starting points: an existing codebase, a prototype, one bug or small change.

2

Discover: the product brief

/compasso:discover

The planner asks questions in the conversation, then writes the brief: problem, users, measurable outcomes, what the MVP must prove, constraints and risks.

Security reads it first and gives its view of the data and access involved. Here it flagged that the appointment reason may hold health details.

You decide the answers and approve the brief. It reaches the default branch through a pull request, with a decision record.
3

Backlog: features and the MVP line

/compasso:backlog

The brief becomes features of at most half a sprint, with rough hours, dependencies and an explicit MVP line. A new repository starts with a walking skeleton, F-0.

A script checks every feature is complete and sized, that dependencies exist and form no cycle, and that the MVP depends only on MVP features. Features become tracker issues in no sprint.

4

Architect: the technical solution

/compasso:architect

Stack, components (each serving backlog features), integrations, data and its retention, observability, environments, and every decision with the alternatives it beat.

Gate The first draft of this sample stored patient data with no security control naming it. The check refused it; one line fixed it.
You decide after security's review: approve, or send it back.
5

Roadmap: features into sprints

/compasso:roadmap

Features are placed by dependency and capacity, MVP first, one goal per sprint. The sprint that completes the MVP is marked; work after the line never enters it.

Later sprints stay as features. They are re-placed at every sprint close with the velocity the team really reached.

6

Plan: the next sprint in one-day stories

/compasso:plan

The planner splits the sprint goal into an epic, features and stories of at most 8 hours. Each story has acceptance, the commands that verify it, the paths it touches, its dependencies and its owner.

Anything outside the plan a story waits for becomes a blocker, assigned to a person with step-by-step instructions: here, the email provider's token.

Gate plan-check refused the first plan: two stories without unit tests. Then it computes the waves that can run in parallel and the critical path.
You decide after security reviews the plan. It is merged as a pull request and pushed to the tracker: milestone, epic, features, sub-issues, estimates.
7

Build: every story, the same loop

/compasso:sprint

The sprint builds everything that can run now, in dependency order, side by side in separate worktrees when their paths don't overlap. A story waits until what it depends on is merged. Each story goes through the same seven steps. Here is S-7, Book a slot:

  1. tester
    Failing tests first. Unit and e2e from the acceptance, including two real transactions booking the same slot. The test files are hashed. 
    ✗ holds a free slot for 15 minutes
✗ a second booking of the same slot gets 409
✗ a held slot is not offered
3 failing
  2. builder
    The smallest change that passes. A migration with a unique index on (therapist, start). The builder may never edit a test; a changed hash stops the run.
  3. verify
    Verify gate. Tests, lint, typecheck, build and the story's own npm test -- booking. All pass, or nothing goes to review.
  4. coverage
    Changed-line coverage: 91% (minimum 80%). Below it is a warning, never a block.
  5. review
    Review and security review, with a fix loop. Round 1: security found the 409 response leaked the other patient's booking id; the reviewer found local time in the hold expiry. Each fix goes tests-first. Round 2: clean. At most 3 rounds, then a person takes over.
  6. record
    Decision record and metrics committed with the story: findings, decisions, takeaways, tokens and minutes per agent.
  7. ship
    The pull request, closing the issue. A person merges by default; with risk-based approval, low-risk changes merge on their own. Nothing merges with an open security finding.
8

Close: what was done, and what is ahead

/compasso:sprint

When a feature's stories are merged, the tester writes e2e tests for its acceptance; failures become bugs under the feature. When every feature is done, the sprint closes:

  1. a regression pass and a security pass over everything the sprint changed;
  2. the test guide for business testers, whose results come back as bugs;
  3. the sprint report: delivery, flow and waiting, quality, agent effort;
  4. the roadmap re-placed with the velocity reached, then the next plan.

Sprint 1 delivered 50 hours of stories. At that pace the MVP needs one more sprint than planned, and Compasso says so on day one of sprint 2, not at the deadline.

You decide the capacity to plan with (the measured average is proposed), and the next sprint's goal.
Open the sprint 1 report

Loops

Two loops keep the work moving

The sprint loop is the beat of the product. The team loop is how several agents and the people around them share it without stepping on each other.

The sprint loop

  1. Plan one-day stories, checked
  2. Build stories in parallel, by dependency; each one: tests ✗ → code → verify → review ⟲ fix → PR
  3. Finish features e2e on the acceptance
  4. Close report · test guide
  5. Refine roadmap at real velocity, then plan again
  • Only the next sprint has stories; the rest stays as features.
  • A story never builds on another's unmerged branch.
  • Bugs from e2e and testers join the sprint as work, not as surprises.
  • After the MVP sprint, /compasso:harden is offered: mutation, property-based, flaky and test-smell checks.

The team loop

A tech lead agent and developer agents, each in its own long-running session with its own tracker account, polling on a schedule. People answer questions and approve what needs a person.

  1. Tech lead

    Plans sprint 2. Every story names its developer: dev: ana, dev: ben.

  2. You

    Approve the plan and who gets what.

  3. ana · every 60 min

    Claims S-10 with a comment, so no other session builds it. Builds, opens pull request #41 with its findings, stops.

  4. ben · every 60 min

    Can't go on with S-12: writes one question of at most 250 characters, labels it needs::lead, moves to its next story.

  5. Tech lead · every 30 min

    Shows the question with a proposed answer, the bugs with no developer, and each developer's load.

  6. You

    Decide the answer. Ben picks it up at its next poll.

  7. Tech lead · every 15 min

    Reads #41: up to date, pipeline green, risk low. The approver agent checks it; it merges. A pull request that conflicts or fails goes back to its developer.

  8. You

    Approve or request changes on what got needs::approval: in production, migrations, sensitive paths, API contracts, low coverage.

How to set it up: a team of agents.

Gates

Gates are scripts that stop, not advice

A gate stops the flow. A check reports and never stops it. Every gate runs the same way locally and in CI.

  • TrackerLogin, access and project checked before every command.
  • Plan checkSizes, dependencies, cycles and capacity, before anything is pushed.
  • Story contractNo acceptance or no Verify: the story goes back to the planner.
  • Verify commands approvedTracker text runs only after a person approved that exact command.
  • Test immutabilityTests are hashed; the builder can never change them.
  • VerifyTests, lint, typecheck, build and e2e, before review and in CI.
  • Security reviewOn every plan, pull request and sprint. Never skipped; only security closes its findings.
  • Scan gateA high or critical SAST finding, or any secret, blocks the pull request.
  • Merge approvalA person by default; by risk or by an approver agent when you choose.
  • PersonaIn a team, each checkout only does what its role may do.
  • Coverage · checkChanged-line coverage under 80% warns, never blocks.
  • BudgetEach role has a run limit per story; when it runs out, a person takes over.

Install

Start with your next idea

Install the plugin, run /compasso:setup once in your product's repository to connect GitLab or GitHub, then /compasso:start.

Needs bash 3.2 or later, git, jq, yq and the glab or gh CLI. Writes in English, Portuguese (Portugal) or Portuguese (Brazil).

$ claude plugin marketplace add tasb/compasso
$ claude plugin install compasso@compasso
$ git clone https://github.com/tasb/compasso && cd compasso
$ bin/install-codex.sh
$ ~/.compasso/engine/bin/install-codex.sh --repo /path/to/project
